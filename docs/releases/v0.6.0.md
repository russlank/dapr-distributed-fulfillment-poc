# v0.6.0: Observability, Scaling, Workflow Versioning, and Comparison (M5)

Milestone M5 of the PoC and the first milestone of its extended tier.
Synthetic data only; not production software. Everything of v0.5.0 (durable
acceptance, execution fence, operator review, inventory with stock actors,
payment and shipping against external simulators, compensation,
cancellation, intervention cases, outboxes, event history, the reconciler)
is still there. See [v0.5.0.md](v0.5.0.md).

## What It Does

- **Alerts, dashboards, runbooks.** The services report the state alerts
  need as gauges, with the thresholds of each time profile applied in the
  service: aging start requests, pending signals, carrier forwards, outbox
  rows (pending, aging, stalled) per source, projection gaps, event dead
  letters, active cases by kind and state, holds past their expiry, and
  carrier callbacks given up. Prometheus evaluates seventeen rules every
  5 s and sends to Alertmanager (a local sink). Grafana provisions eight
  dashboards. Every alert has a runbook entry in the operations guide.
  A unit test refuses log message placeholders that could carry payloads,
  secrets, or personal data.
- **Every alert checked in a drill.** Each rule fires in the drill that
  causes its condition and resolves after recovery. A drill fails if the
  alert was already firing before its fault, because the check could not
  attribute it.
- **A confirmed delivery failure ends the order.** An operator's
  `ConfirmExternalFailure` on a `DeliveryException` or `DeliveryOverdue`
  case moves the order to the terminal status `Escalated` (reason
  `DeliveryFailed`). The case stays open as `Escalated` until a person
  records the business resolution (`Acknowledge`). Nothing is refunded,
  reshipped, or restocked automatically. An escalated case counts as active,
  so an order never gets a second case of the same kind.
- **Workflow versioning.** A change to the fulfillment workflow's path is
  guarded by a named patch (Dapr's `IsPatched`). A run that starts with the
  patch takes the new path and records the patch in its history. An
  instance started before the patch replays its recorded path. A host can
  hold a patch back (`WORKFLOW_PATCHES_DISABLED`), so a change rolls out
  replica by replica. Each host reports its patches at
  `/system/workflow-patches`. The first patch, `execution-version-2`,
  records which version executed an order
  (`WorkflowStartRequest.ExecutionVersion`).
- **Runtime-store outages.** A cut to the workflow state store stops
  workflow progress but not business commits. After the restore every order
  completes once, with nothing lost or repeated. With the Scheduler down,
  review deadlines expire late but correctly. With Placement down, orders
  wait and then complete.
- **The reconciler is quieter.** It no longer reports designed waits as
  stalled: a delivery wait, or a review still within its deadline. A gap
  whose missing event the consumer rejected for a reason a replay cannot
  change is reported once as unresolvable, with a `ProjectionGap` case.
  Before, it was replayed on every pass.
- **Scaling.** The same client load runs with one, three, and five compute
  replicas, and one replica is killed during the last run. Every order
  completes, the work spreads over the running replicas, and the killed
  replica loses and repeats nothing. A sidecar setting caps activity
  concurrency per replica, and the cap holds under load.
- **Stock actors compared with SQL-only coordination.** Both modes run the
  same contention scenario (500 one-unit orders for 100 units, 32 in
  flight). They give the same result, with close throughput and latency.
  Without the actors, SQL Server carries the contention: about 30 % more
  peak sessions, 20 % more lock wait, and 240 MiB more memory. The observed
  hold durations (seconds) size the hold lifetime. Details:
  [dapr-vs-alternatives.md](../dapr-vs-alternatives.md).
- **Security boundary scenario.** S22 checks every trust boundary: role
  keys, the app and sidecar tokens, who may manage workflows, the carrier
  signature, and database logins. It also checks that no secret value
  appears in any container log.
- **Kubernetes template.** `deploy/kubernetes/` is a generic Kustomize base
  for the services on a cluster with Dapr. It is **not verified on a
  cluster**: it renders with `kubectl kustomize`, nothing more. See
  [its README](../../deploy/kubernetes/README.md).

Proven by scenario scripts and failure drills that print `PASS`/`FAIL` from
real runs on a stack with two or three replicas per role (five compute
replicas for scaling).

|---|---|
| Every alert rule fires during the fault that causes it and resolves after recovery | R06, R07, R08, R12-R16, R20, R28, R29, R30, R32, R33 |

## Found on the Way

- **Terminating a patched workflow stalls it for good (Dapr 1.19.1).**
  Terminating or purging an instance whose history recorded a patch never
  answers, and the instance stays `Stalled`, also across host and sidecar
  restarts. Unpatched instances terminate in about 1 s. See the known
  limitations.
- **A rejected event was replayed forever.** The alert checks showed a gap
  alert and dead letters that never cleared, which led to the reconciler
  change above.
- **Two replicas raced to create the failpoint table** of a drill build on
  a fresh database, and one exited. The creation is now serialized.
- **R12's end check read the last history row.** When Shipping stays down
  past the delivery deadline, the workflow completes the order through its
  carrier poll, and the queued `Delivered` forwarded afterwards adds an
  audit row. The drill now checks the order's last real transition.
- **SQL Server ran out of memory** once during a SQL-only contention run on
  a stack that had run for three hours. On fresh volumes both modes passed.

Details: [journal.md](../journal.md).

## Known Limitations

- **Patched workflow instances are never terminated or purged.** On Dapr
  1.19.1 such an instance stays `Stalled` for good, and with
  `execution-version-2` enabled every new order is patched. This needs no
  workaround in normal operation: SQL Server owns the order's state, and
  the workflow re-reads it at every step and completes as fenced once the
  order is final. An order is stopped through its own paths (cancellation
  before dispatch, review and case resolutions, `Repair`), and the workflow
  ends itself. The gap: an instance terminated anyway is not repaired
  automatically, because the reconciler treats `Stalled` as running. Two
  candidate remedies, neither implemented nor demonstrated: Dapr's force
  purge, which would turn the instance into a missing workflow that the
  reconciler already repairs, and a reconciler rule for instances that stay
  stalled while no patch is held back. The Dapr 1.19.2 release notes list
  no fix. Operations guide: "Never Terminate a Patched Workflow".
- **Verified on Docker Compose only.** The Kubernetes template is
  untested; mTLS between sidecars, access-control policies, and production
  high availability are deployment design work.
- **Alert thresholds are fixed per time profile**, and the local SQL Server
  (2 GiB) has little memory headroom for long SQL-only runs.
- Unchanged from v0.5.0:
  - the consumer's lock deadlocks under load (retried, harmless);
  - a lost delivery-deadline timer is not nudged;
  - the timeline is a read model;
  - hold lifetime versus long pauses before the capture;
  - no reason code names an expired authorization;
  - packing is simulated per line;
  - no partial shipment, capture, or refund;
  - static API keys.
