# v0.5.0: Reliable Event Distribution, History, and Recovery (M4)

Milestone M4 of the PoC and the last milestone of its core tier. Synthetic
data only; not production software. Everything of v0.4.0 (durable
acceptance, execution fence, operator review, inventory with stock actors,
payment and shipping against external simulators, compensation,
cancellation, intervention cases) is still there. The events those services
already wrote are now published, projected, and reconciled. See
[v0.4.0.md](v0.4.0.md).

## What It Does

- **Outboxes in every owning service.** The order API, inventory, payment,
  and shipping services write each business event in the same transaction
  as the fact it describes, into their own database's outbox, with a
  gapless sequence per order and source. Rows are never deleted.
- **Relays, at least once.** A leased relay in every replica publishes
  pending rows through Dapr pub/sub (RabbitMQ). It backs off on failure,
  flags rows that keep failing as `Stalled` while retrying them, and takes
  over the rows of a replica that died. Marking a row `Published` is guarded
  by a replay generation, so a replay requested between a publication and
  its mark is never swallowed. Any source can be replayed by order and
  sequence.
- **Event history and timeline.** The order API stores every valid event
  once per event id and counts duplicates. It keeps each order's current
  state per source contiguous: an event that arrives early waits as pending
  until the gap before it is filled, then is applied in sequence. Conflicting
  payloads, a sequence taken by another event, a wrong source, an unknown
  schema version, or an unreadable message are recorded in a dead-letter
  table with ids and reasons only. A message the consumer keeps failing on
  reaches the dead-letter topic after a bounded number of redeliveries.
  Admin endpoints show an order's timeline (combined stage, per-source
  state, pending events, dead letters), a checksum, and rebuild current
  state from history, comparing each stream with its live state.
- **Reconciler.** One leased instance compares workflows with SQL and opens
  one case per order and kind: `WorkflowFaulted`, `WorkflowMissing`, or
  `ExecutionMismatch`. Resolving such a case compensates before the point of
  no return (`WorkflowFailed`), or finalizes after Shipping shows the order
  delivered. It nudges review waits whose timer was lost. It also replays
  outbox events for projection gaps and for streams whose source is ahead
  of the timeline, including a lost last event.
- **Carrier hardening.** The carrier simulator keeps every callback
  receiver after a restart, retries callbacks for about a minute in drill
  builds, and has test modes that lose callbacks (`Lost`) or callbacks and
  status queries (`LostNoPoll`). The carrier forwarder has a drill profile.
- **Verification runner.** `scripts/verify.sh` runs the gates, integration
  tests, and every scenario and drill on fresh stacks (`--suite full`), or
  groups of them on a running stack during development (`--suite dev`,
  `--only`, `--reuse`). It records per-step timings and keeps the order API
  logs of each drill phase. The release stack's scenarios run with the
  carrier simulator at a 2 s step and take about half the time they did.

## Verified Guarantees

Proven by scenario scripts and failure drills that print `PASS`/`FAIL` from
real runs on a stack with two or three replicas per role. They inject real
failures (broker outage, process kills, failpoints, lost callbacks, purged
workflow instances) and read every database.

| Guarantee | Evidence |
|---|---|
| Business commits continue while the broker is down; the outboxes hold the backlog, nothing is lost, and the published and stored event sets converge afterwards | R14 (S11) |
| An event published again and again (relay crashes after the broker's acknowledgement, replays of all four sources) is applied once; history and state do not change | R15 (S12, S18) |
| Events arriving out of order, duplicated, or with a conflicting payload give the same state as in-order delivery; the conflict is recorded and changes nothing | S48 (S43 events); 720 permutations in the unit tests |
| A lost event is detected as a gap, later events wait, and the reconciler's replay fills the gap | R32 (S48, S18) |
| Malformed, unknown-schema, and poison messages are dead-lettered without blocking other orders, and no payload reaches the logs | R16 (S18, S20) |
| Every source's published events reach the history once, in order, and a rebuild of every stream on the stack equals live state | S01 |
| A faulted, a missing, and a mismatched workflow are each found by the reconciler as one case and repaired | R30 (S44) |
| Carrier callbacks survive an unavailable order API and an unavailable Shipping | R12 (S28) |
| Lost callbacks do not leave an order waiting forever: the deadline poll, or a `DeliveryOverdue` case, completes it | R29 (S42) |
| A redelivered review signal is a no-op; the order progresses once | R23 (signal part) |

Every M1, M2, and M3 scenario and drill passes again on this release.
Integration tests cover the outbox relays (leases, generation-guarded
marking, replay) and the event consumer (pending and drain, duplicates,
conflicts, concurrent deliveries of one order, rebuild, and repair of a
stream left behind its history).

Functional acceptance: commit `c92bb30` (clean tree, fresh volumes: gates,
unit and integration tests, every M1 to M4 scenario and drill). The release
commit adds only the version, these notes, and documentation; it is verified
by its own complete run before the tag.

## Found on the Way

A full run left one order's inventory stream behind its own history, and
the reconciler's replays could not repair it. It showed up once per run, in
one stream among about 2,100. The cause was a deadlock between ingests of
neighbouring streams in the consumer's own row lock. When SQL Server picked
the lock's second statement as the victim, the database client did not
raise the error, and the rest of that ingest ran without its transaction
and lock. Every statement of the consumer now refuses to run without a
transaction, and a duplicate or early delivery also repairs a stream left
behind its history (logged and counted as `event_stream_repairs_total`).
Details: [journal.md](../journal.md).

## Known Limitations

- **A failed delivery has no business end yet** (unchanged from v0.4.0).
  When a delivery fails after the dispatch, the intervention case makes it
  visible, and only `ConfirmExternalSuccess` completes the order. Any other
  resolution is recorded and the order returns to `AwaitingDelivery`, with
  the payment captured and the stock consumed. Such orders must be found by
  their resolved cases and handled outside the system until a business
  policy is defined.
- **The consumer's lock deadlocks under load.** Ingests of neighbouring
  streams deadlock now and then (a few dozen per full verification run).
  Each deadlock is retried by the broker and is harmless, but it costs
  latency.
- **Reconciler thresholds are fixed multiples of the stage timeouts.** A
  stream that stays behind is replayed on every pass until it catches up.
  Counters exist but are not alerted on yet (M5).
- **A lost delivery-deadline timer is not nudged.** Only review waits are
  nudged. A stuck delivery wait shows up through the stage-threshold check
  only when its workflow is no longer running.
- **The timeline is a read model.** Orders, holds, payments, and shipments
  never depend on it. A rebuild restores it from history.
- Unchanged from v0.4.0:
  - hold lifetime versus long pauses before the capture;
  - no reason code names an expired authorization;
  - packing is simulated per line;
  - no partial shipment, capture, or refund;
  - local Docker Compose only, static API keys, no Dapr mTLS.

```bash
bash scripts/stack-up.sh --drill --replicas
bash scripts/scenarios/S01-happy-path-events.sh
bash scripts/drills/R14-broker-outage.sh               # and the other drills
```
