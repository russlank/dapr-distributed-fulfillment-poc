# v0.3.0: Inventory Contention and Idempotent Activities (M2)

Milestone M2 of the PoC. Synthetic data only; not production software.
Everything of v0.2.0 (durable acceptance, execution fence, operator review,
client simulator) is unchanged; see [v0.2.0.md](v0.2.0.md).

## What It Does

- **Inventory database:** the inventory service owns `InventoryDb` with its
  own migrations (job `inventory-db-migrate`; the service refuses an older
  schema). Warehouses `W1`-`W3` with an allocation priority; stock rows with
  `OnHand` and `Reserved`, held to `0 <= Reserved <= OnHand` by check
  constraints; holds per order line that leave `Held` once (`Released`,
  `Expired`, or `Consumed`); a stored result per operation key; one outbox
  event per hold transition with a gapless sequence per order.
- **Guarded operations:** reserve, release, consume, and expire are
  conditional SQL in one transaction each, under an exclusive lock on the
  order, with the stored result read first (a repeat returns it). The
  guarantees live in SQL, not in the actors.
- **Stock actors:** one actor per warehouse and SKU serializes reservations
  and releases of that stock row, so a hot SKU queues in the actor; Dapr
  Placement moves the actor when its replica dies. The actors hold no state.
- **SQL-only comparison mode:** `INVENTORY_COORDINATION=SqlOnly` runs the same
  operations without actors, directly from any inventory replica.
- **Allocation:** every line whole from the first warehouse by priority that
  can serve it, never split; lines are reserved in deterministic SKU order,
  and a transaction that touches several stock rows locks them in
  `(warehouse, SKU)` order.
- **Fulfillment with reservation:** after validation, checks, and an
  approved review if required, the workflow reserves every line, runs the
  simulated payment and shipment steps, and consumes all of the order's
  holds in one transaction (or none of them).
- **Compensation:** a line no warehouse can serve releases the earlier lines'
  holds and rejects the order (`Rejected`, `InsufficientStock`); a
  reservation that keeps failing, or a hold that expired before consumption,
  releases every hold and ends `Compensated` (`ReservationFailed`,
  `ReservationExpired`). The order is closed for reservations first, so a
  late retry cannot add a hold.
- **Expiry recovery:** holds live 30 minutes by SQL time
  (`INVENTORY_HOLD_TTL`). A sweeper on every inventory replica, one at a time
  through a SQL lease, expires due holds; it uses neither the Dapr Scheduler
  nor Placement, so holds expire while those are down.
- **Client simulator:** `contention` sends many one-line orders for one SKU.

## Verified Guarantees

Proven by scenario scripts and failure drills that print `PASS`/`FAIL` from
real runs and read the databases. Every inventory run checks the SQL
invariants: `Reserved` equals the units of the held holds of each row, every
hold has one creation and one closing event, and each order's outbox
sequence is gapless.

| Guarantee | Evidence |
|---|---|
| No oversell under contention: 500 one-unit orders for 100 units give exactly 100 completions, with or without actors | S03 (actor and SQL-only mode); integration tests: 60 concurrent reservations of a row of 20 succeed 20 times |
| A crash after the reservation committed, before Dapr learned of it, applies the reservation once | R04 (S05) |
| Killing the replica that hosts a hot SKU's stock actor, under contention, moves the actor and loses or doubles no unit | R05 (S07) |
| Holds that expire while the whole inventory is down compensate their orders; orders accepted meanwhile complete | R06 inventory (S08) |
| A partial reservation is released exactly once, with no hold for the failed line | R08 A (S45), R08 B, S20 |
| Holds expire with the Dapr Scheduler and Placement stopped | R08 C (S15) |
| A failing order does not block other orders of the same SKU | S20 |
| Repeats of one operation key, racing, produce one effect; consumption racing expiry closes a hold once | integration tests |

Every M1 scenario and drill passes again on this release.

## Known Limitations

- **Hold lifetime versus the time to consume (significant for M3).** A hold
  must be consumed within its lifetime, or the order is compensated
  (`ReservationExpired`); it is never oversold. Today the time between
  reservation and consumption is the simulated steps (seconds). Real payment
  authorization, shipment, and intervention pauses (M3) lengthen it, and
  their interplay with the hold lifetime is still to be designed.
- Outbox events are written but not published (M4).
- The order's execution view does not show inventory rows yet; inspect them
  with SQL ([operations.md](../operations.md#inventory)).
- No restock path: stock comes from the migration's seed (scenarios set their
  own rows with test-only SQL).
- The latency a stock actor adds on a hot SKU is not measured yet (M5).
- Unchanged from v0.2.0: a failed workflow waiting for review is not
  recovered automatically (M4 reconciler); one line per SKU per order; a few
  seconds of failing invocations after a workflow-host replica restarts; the
  intermittent integration-test failure at fixture start; local Docker
  Compose only, static API keys, no Dapr mTLS.

## Deferred

- **M3:** payment through the external provider simulator (authorization,
  capture, void, refund, ambiguous outcomes), shipping and carrier callbacks,
  cancellation and the point of no return, the full review lifecycle,
  intervention cases.
- **M4:** event distribution (outbox publication, broker, projection), the
  reconciler.
- **M5:** alerts and dashboards, performance and scaling runs (including the
  actor versus SQL-only comparison), workflow upgrades, Kubernetes.
