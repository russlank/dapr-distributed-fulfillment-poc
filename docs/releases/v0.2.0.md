# v0.2.0: Durable Order Acceptance, Execution Fence, Cross-Replica Work (M1)

Milestone M1 of the PoC. Synthetic data only; not production software.

## What It Does

- **Order acceptance:** `POST /orders` with an idempotency key and a request
  hash; one transaction writes the order, its lines, the first status row,
  the key, and one workflow start request. A repeated key with the same body
  returns the original order; with another body `422`. Any order API replica
  accepts any request.
- **Starting workflows:** a start dispatcher in every order API replica
  claims start requests with lease tokens and starts each order's workflow
  through the workflow host's management API; never directly through the
  order API's sidecar. A terminal order's start request is closed without a
  start.
- **Execution fence:** every workflow run claims the order first; a run on a
  terminal order adds no business effect.
- **Fulfillment (simulated):** validation, price and risk checks in parallel
  on the compute workers, then simulated `stub-` steps and one terminal
  transaction (`Completed`, start request `Closed`). Every business effect is
  keyed and stored once.
- **Operator review:** orders from 1,000.00 wait (`AwaitingApproval`) for a
  decision through `POST /reviews/{id}/decision` (operator key); the decision
  is decided in SQL with an immutable audit row and a pending signal that the
  signal dispatcher delivers to the waiting workflow; the workflow also reads
  SQL when its timer fires. Expiry opens a second round, then rejects.
- **Client simulator:** an external HTTP client (no Dapr) with seeded,
  replayable workloads, duplicates, conflicts, approvals, and inspection;
  retries of ambiguous answers with the same key; JSON results and exit codes.
- **Diagnostics:** an admin execution view per order (start, attempts,
  checks, effects, reviews, signals, workflow state); every order API answer
  names its replica (`X-Served-By`); traces and metrics through OpenTelemetry.

## Verified Guarantees

Proven by scenario scripts and failure drills that print `PASS`/`FAIL` from
real runs and read the databases:

| Guarantee | Evidence |
|---|---|
| A duplicate submission, on any replica and at the same time, creates one order and one set of effects | S04, S23, ACC |
| A lost answer, a timeout, or a dropped request never duplicates an order; a retry with the same key returns the committed order | S24 (network faults), R03 (answer lost after the commit, in-server failpoint) |
| Another body under a used key is refused by every replica; the stored order does not change | S43 |
| A start is effective once: crashes after acceptance or after the start claim, a reset start request, or a directly scheduled completed instance add no business effect | R02 A-D, S49, S51 |
| A waiting workflow survives the loss of its host; an approval through another replica reaches it | R01, S09, S52 |
| Work waits while the compute pool is down and completes once afterwards | R06 (compute), S02 |
| A process ending after a commit and before its result reaches Dapr does not duplicate the effect | R00 |

Functional acceptance: commit `4decce0` (clean tree, fresh volumes: unit and
integration tests, every scenario and drill above). The release commit adds
only result attribution in the scripts, the version, and these notes; it was
verified again before tagging.

## Known Limitations

- **A failed workflow waiting for review is not recovered automatically.** If
  a fulfillment workflow fails or disappears while its order is
  `AwaitingApproval`, the decision is still recorded and its signal ends
  `Stuck` or `Discarded`, but nothing resumes the order. It stays visible
  (execution view: failed workflow or stuck signal) until the reconciler
  arrives (M4); until then an operator has to notice it.
- One line per SKU per order (a validation rule of this PoC, not of Dapr).
- Reservation, payment, and shipping are simulated (`stub-` effects).
- After a workflow-host replica restarts, invocations through the sidecars
  can fail for a few seconds; delivery is retried (cause not established).
- The intermittent integration-test failure at fixture start (the test
  container reaper disappearing) is not explained yet.
- Local Docker Compose only; static API keys; no Dapr mTLS (Kubernetes and
  mTLS come later).

## Deferred

- **M2:** inventory with actors and SQL-backed reservations, contention,
  idempotent inventory activities, holds that expire (the inventory variant

- **M3:** payment through the external provider simulator, carrier callbacks,
  manual escalation, cancellation, intervention cases.
- **M4:** event distribution (outbox, broker, projection), the reconciler.
- **M5:** alerts and Grafana dashboards, performance and scaling runs,
  workflow upgrades, Kubernetes.
